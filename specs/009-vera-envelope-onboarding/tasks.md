# Feature 009 — Vera Envelope Onboarding ("Vera's First Day"): Task List

**Branch**: `009-vera-envelope-onboarding` · **Scope**: the on-ramp only — **data receipt → verified live envelope, shadow-ready**: chain-of-custody vault receipt, format discovery, ingest/normalization to the canonical practice model, completeness-and-quality verification (financials/AR/inventory included), an owner-trusted reconciliation report, identity/`entity_ref` bootstrap that hands off to 011, and the criteria that mark a practice shadow-ready — under a hard invisible-adoption constraint, generalizing across mixed PIMS via a pluggable adapter port. Ongoing envelope operations (delta sync, dual-path writes, the shadow/advise engine, verb promotion, the Phase-D cutover/Replace event) are **out of scope** (010/011/envelope-MVP): this list **ends at `shadow_ready`**. Per the implementation-reality binding, **everything external runs in sim/dual-mode** — the clinic-owned vault, the secure-file-transfer intake, and the Gemini extraction subprocessor all get simulator counterparts mirroring `backend/sms_gateway.py`'s auto-detect pattern, and the whole pipeline runs against a **synthetic ezyVet-shaped complete-export fixture** (built as T005). The entire list is completable and testable with **zero live subprocessor / secure-transfer / real-PII calls**. Live-mode is a config swap, deferred to the Pilot-Activation section.

**Datastore for this build**: the net-new onboarding-control tables + the net-new canonical financial/AR/ledger/payment + inventory tables run on a **local PostgreSQL via `docker-compose`** (the shipped `vetagent-voice-pg` container, host port **5433**, `VOICE_DATABASE_URL` convention — matching the data-model's "Postgres + RLS, not SQLite" mandate; R8: never another port/container). **FORCE-RLS on all onboarding-control tables (SEC-20)** and app-level `clinic_id`/`practice_id` scoping stand in for full RLS in the single-clinic build (per the plan's VP-1-slip degradation, same posture as 010/011). Provisioning **wraps the full transaction** (the FarmAgent orphan-account bug: a rolled-back receipt leaves no partial vault/lineage rows). The **demo repo's SQLite is not used** — the envelope plane (chain-of-custody + reconciliation + identity-audit) needs Postgres; the platform/envelope track does not regress to SQLite.

**Coverage**: FR-001–FR-033 (all 33 owned by ≥1 task) · SC-001–SC-010 (SC-007 timing is **Pilot-Activation-homed** — the build has no wall-clock proxy; only its enablers are build-proven via T033/T044/SC-010) · data-model onboarding-control tables + canonical-model extensions (authored in `data-model.md` — the T002 entity source of truth) · contracts `pims-adapter-port.md` (T017), `reconciliation-report.md` (T027), `identity-handoff.md` (T030 — the 009-defined 011 seam). **45 tasks total** (target ~35–45).

**Path note (plan reconciliation)**: The plan's structure lists the 009 tier as `backend/envelope/` — distinct from spec-008's **native** onboarding at `backend/onboarding_repository.py` / `backend/agents/onboarding_agent.py` (do **not** collide). All existing Python (`models.py`, `agents/`, `sms_gateway.py`, `voice/`, `relationship/`) lives under `backend/`, so 009 code roots at **`backend/envelope/`**; config stays at repo-root **`config/envelope/`**; tests under **`backend/tests/envelope/`**. Models extend the shared **`backend/models.py`** (010/011 precedent). `backend/relationship/entity_ref.py` (011 T005) and `backend/relationship/review_queue.py` (011 T012) are **reused verbatim** — 009 imports them, never forks them.

**Legend**: `[P]` parallelizable · `[US#]` maps to spec user story · `[MARKETING]` customer-visible / announcement-blocking · `[REUSE]` imports shipped 010/011 core verbatim (no duplication; the shipped module keeps its API) · `[CONTRACT]` freezes a cross-team seam doc under `contracts/`.
